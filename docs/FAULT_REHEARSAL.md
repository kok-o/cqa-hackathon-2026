# Реальные прогоны пограничных случаев

Проверено 7 ноября 2026 года для SetW. Это дополнение к
[аудиту требований](READINESS_AUDIT.md): здесь перечислены выполненные прогоны,
обнаруженные дефекты и ограничения. Сценарии не заменяют неизвестные десять
контрольных чатов организаторов и не измеряют точность по их Ground Truth.

## Подтверждённый результат

- **166 backend-тестов прошли**. Внутри одного теста арифметики перебраны все
  **5 184** допустимые комбинации официальных ответов и N/A. Независимый расчёт
  через рациональные числа проверяет итог и округление; отдельно проверены
  перестановка результатов критериев, масштабирование весов и отсутствие итога при needs_review.
  Повтор на чистой копии без `.env` и `data/evaluations` также прошёл: CI выявил
  зависимость одного нового теста от существования папки, подготовка исправлена.
- **15 браузерных сценариев со сбоями прошли** на настоящем локальном HTTP API.
  Оценщик в них механический; это проверка приложения без платных вызовов.
- **7 сценариев HTTP/процессов прошли**: реальные параллельные запросы,
  имитация сбоев провайдера, принудительная остановка и повторный запуск
  собственного тестового процесса с временной SQLite.
- Сборка TypeScript/Vite, обычный браузерный smoke и повторная проверка импорта,
  пакета десяти чатов, аудио и адаптивного интерфейса выполнены отдельно.
- **Живая Luna/high/v6 завершила 12/12 синтетических диалогов** во втором полном
  проходе. Совпали 25/25 заранее заданных узких решений, 12/12 отношений между
  парами, 4/4 опорных цитаты нарушений. Это пересекающиеся проверки, а не 41
  независимое испытание и не оценка всех 96 ответов восьми критериев человеком.

Компактные машинные свидетельства находятся в [validation](validation/).
Полные исходные модельные ответы и журналы локально сохранены в игнорируемой
папке `data/evaluations/`; настоящие клиентские записи и ключи в отчёт не включены.

## Найденные дефекты и исправления

| Ситуация | Наблюдение до исправления | Проверенное поведение после |
|---|---|---|
| Сервер принял POST, ответ потерялся | Оценка уже сохранена, UI сообщает неуспех; новый ручной запуск создавал новый ключ | Ключ сохраняется до отправки. Повторы возвращают тот же job; 2 POST → 1 job → 1 оценка |
| Потеря всех трёх ответов, обновление вкладки | У браузера нет надёжного пути к исходной задаче | Продолжение использует сохранённый ключ; в очереди из трёх диалогов ровно три оценки |
| 503 при опросе или длительный Retry-After | Временный сбой прерывал работу; cooldown провайдера игнорировался | Ограниченные безопасные повторы; длинный cooldown останавливает автоматические попытки |
| Провайдер присылает ответ понемногу | HTTPX ограничивал бездействие, но не полное время запроса | Общий deadline каждой попытки; реальный trickle-тест завершается, максимум две попытки |
| Старая задача завершилась после новой | Старый снимок скрывал актуальный результат в сводке; мешал выбору экспорта | Сводка, исходный выбор UI и официальный экспорт выбирают последний подходящий текущему снимку результат |
| Запоздавшая загрузка истории | Могла затереть только что показанную оценку до обновления страницы | История объединяется с уже полученными результатами, сохраняет свежую ревизию и выбор |
| У провайдера ошибка после потраченных токенов | Failed job терял диагностическую usage и стоимость | Сохраняет безопасные error_code/model_info; неизвестная полная цена остаётся null |
| HTTP 200 с null/обрезанным JSON-объектом | Типизация TypeScript не проверяла полученные данные; возможны потеря восстановления и блокировка запуска | Runtime-проверки конфигурации, job, оценки и истории; ошибочный ответ не меняет сохранённую идентичность задачи |
| Ответ другого job или версии чек-листа | Валидная структура могла быть принята как нужный результат | Проверяются job ID, evaluation ID, группа/диалог и версия правил; очередь сохраняется |
| Казахский ID в Windows cp1251 | Вывод прогресса бросал UnicodeEncodeError и прерывал соседние модельные запросы | Безопасный вывод с escape для неподдерживаемых символов; регрессия с настоящим строгим cp1251-потоком и параллельными задачами |

Метаданные ответа провайдера также проверяются на совпадение с настроенным
секретом; тестовый секрет не появляется в ответах API и журнале. Это проверка
конкретных путей утечки, а не полный аудит безопасности приложения.

## Что именно выполнено в браузере

Прогон [browser_faults.py](../scripts/browser_faults.py) действительно отправляет
запросы серверу. Потерю ответа моделирует **после** принятия запроса через
Playwright `route.fetch()`, затем `route.abort()`. Быстрому механическому
оценщику в двух сценариях временно показывается queued, чтобы гарантированно
проверить polling; реальные job ID и сохранённые результаты не подменяются.

| № | Сценарий | Проверяемый итог |
|---|---|---|
| 1 | Потерян один ответ принятого POST | 2 HTTP-запроса, один ключ, одна задача, одна оценка |
| 2 | Первый polling отвечает 503 | Восстановление, одна оценка |
| 3 | Потеря всех ответов POST → reload → resume | Исходный job найден по ключу; три оценки на три исходника |
| 4 | Reload во время активной очереди | Остаток продолжен без дублей |
| 5 | Остановить после текущего → продолжить | Все три исходника обработаны однократно |
| 6 | Принятый POST возвращает null | Ключ сохранён, продолжение находит прежнюю задачу |
| 7 | Получение оценки возвращает обрезанный объект | Job сохранён, после восстановления результат открыт |
| 8 | HTTP 429 с HTML и Retry-After: 60 | Один автоматический запрос, затем пауза; ручное продолжение после снятия fault |
| 9 | Конфигурация возвращает null | Нет отправки оценки; следующий запуск после восстановления работает |
| 10 | Polling возвращает другой job ID | Исходный job не перезаписан, восстановление без дубля |
| 11 | Ответ содержит другую версию правил | Результат не принят, продолжение с прежним job |
| 12 | Пустая старая история приходит после новой оценки | Свежая оценка остаётся выбранной |
| 13 | Более поздняя запись относится к старому исходнику | Автоматически выбран результат текущего исходника |
| 14 | HTML/onerror в тексте реплики | Отображается обычным текстом, код не исполняется |
| 15 | Повреждённая сохранённая очередь | Рабочая область открывается без JS-ошибки |

## Живой модельный прогон и расходы

[Синтетический набор](../fixtures/adversarial/README.md) включает RU и KZ:
изменение только ID/времени, 24 повторные инструкции от бота/клиента,
цитирование чужого оскорбления против прямого оскорбления оператором,
отозванное предположение против раскрытия личных данных без идентификации,
четыре диалога по 260 реплик с контрольными парами и нарушением в середине/конце.

Ожидания зафиксированы и просмотрены другим ассистентом **до** ответов модели.
Expected/relations не отправляются провайдеру. Между двумя проходами все
12 запросов, тексты и ожидания остались теми же; исправлялся вывод runner.

| Метрика | Первый запуск + продолжение | Повтор после исправления вывода |
|---|---:|---:|
| Завершённые диалоги | 10/12 | 12/12 |
| Неизвестный итог после прерывания | 2 | 0 |
| Авторские решения | 21/25, четыре недоступны | 25/25 |
| Отношения пар | 8/12, четыре недоступны | 12/12 |
| Опорные цитаты нарушений | 4/4 | 4/4 |
| Повторы evaluator | 1 | 0 |
| Дословные цитаты / проверенные диапазоны | 107/107 и 11/11 | 142/142 и 13/13 |
| Известный расход USD | 0.02439559 | 0.01729600 |
| Полный расход | Неизвестен | 0.01729600 |

Первая попытка одного длинного KZ-контроля содержала неточную цитату.
Валидатор отклонил её; разрешённый повтор исправил ответ. Ошибка Windows
оборвала два других запроса, их результаты и usage неизвестны. Они не были
автоматически повторены при resume, а сохранились как interrupted_unknown.
Первый незавершённый проход сохранён отдельно и не заменён удачным отчётом.

Во втором проходе среднее время диалога — 24.05 с, медиана — 17.79 с,
максимум — 62.86 с. JSON-проверка: 12 ok / 0 error; осталось предупреждение
для N/A discovery у `adv-long-ru-control`: нет supporting source turns.
Это не ошибка схемы, но такой ответ хуже объясняет неприменимость.

**Известный подытог обоих проходов — $0.04169159.** Полная фактическая цена
неизвестна из-за двух прерванных запросов. На них удержан расчётный резерв
$0.04764950; сумма известных расходов и резерва — **$0.08934109** при общем
лимите $0.25. Резерв не является фактически списанной суммой. Цены рассчитаны
по usage и настроенным тарифам, а не по счёту провайдера. Второй проход повторяет
запросы и использует прогретый кеш; его цену нельзя переносить на новый PROD.
Sol и Astra в этих прогонах не вызывались.

## Повторение без платных вызовов

Из корня проекта после обычной установки зависимостей:

```powershell
.venv/Scripts/python.exe -X utf8 -m unittest discover -s backend/tests -v
npm --prefix frontend run build
.venv/Scripts/python.exe -X utf8 scripts/fault_http_rehearsal.py --out scratch/fault-http.json
```

Для браузера нужен Python с `httpx`, `playwright` и установленный Chrome
(локальные прогоны использовали global Python; сервер — `.venv`). В первом
терминале запустить отдельный сервер с временной БД и механическим оценщиком:

```powershell
.venv/Scripts/python.exe -X utf8 scripts/ui_test_server.py --port 8024
```

В другом терминале последовательно:

```powershell
python -X utf8 scripts/browser_faults.py --url http://127.0.0.1:8024
python -X utf8 scripts/browser_smoke.py --url http://127.0.0.1:8024
python -X utf8 scripts/browser_readiness.py --url http://127.0.0.1:8024
```

`browser_faults` отказывается изменять сервер без явного `mode=test`; все
тестовые группы имеют уникальные ID. Сервер остановить Ctrl+C после проверки.
Команды платного plan/live/report вынесены в [README набора](../fixtures/adversarial/README.md).
Для нового модельного запуска нужен новый каталог: freeze проверяет hashes кода
и данных. Старые отчёты сохранены; после изменения runner нельзя повторно
создать отчёт старого плана текущим кодом без восстановления той версии.

## Оставшиеся границы

После обновления рабочего приложения на порту 8015 сохранены 65 диалогов,
137 оценок и 137 задач. Активных задач перед перезапуском не было; создана
резервная копия SQLite. Повторная выгрузка через UI совпала с существующим
DEV results.json: 65 ok. Проверки рабочего приложения были только читающими,
новых платных оценок не создавали. Панель продолжения очереди отдельно
проверена при ширине 1440/768/390 px, без горизонтального переполнения.

Эта проверка повышает надёжность демонстрации, но не гарантирует топ-50.
Нужна независимая разметка новых диалогов по всем восьми критериям, особенно
пограничным C2/C3/C4/C7. Эти 12 случаев главным образом проверяют C1/C8 и
один C3; EN, произвольные длинные реальные диалоги и аудио здесь не оценивались.

Приложение по-прежнему локальное: один процесс и SQLite, очередь вкладки
в sessionStorage. Закрытие вкладки, ручная очистка её хранилища, несколько
независимых вкладок/пользователей и промышленная нагрузка не покрываются
гарантией однократности. Не начатый диалог берётся с сервера в момент первого
POST; не меняйте исходники и настройки провайдера во время контрольного прогона.
История и принятые задачи сохраняются сервером, но прерванный запрос может быть
оплачен провайдеру без доступного результата. Подтверждённые failed задачи
нужно разбирать отдельно, а не скрывать нулём или готовым ответом.
