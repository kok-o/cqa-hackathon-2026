# План реализации за 24 часа

## Результат

Оператор или руководитель открывает диалог, выбирает версию чек-листа и запускает проверку. По каждому критерию он видит ответ, баллы, объяснение и ссылку на доказательство. Спорный критерий можно отправить на пересмотр. Проверяющий сохраняет решение и причину, после чего система пересчитывает итог. Изменённый через интерфейс критерий участвует в следующей проверке.

Основной документ — [CQA Student Guide](briefs/CQA_Student_Guide.pdf), страницы 1–4. DEV содержит 65 диалогов, включая 60 синтетических чатов и пять реальных звонков. Языки набора RU, KZ и EN. Транскрипты уже предоставлены.

## До начала параллельной работы

За первые 30–45 минут команда принимает шесть решений.

1. Уточнить реальный T0, адрес DEV, контрольный group_id и способ передачи репозитория.
2. Получить второй PDF с восемью критериями. Переписать веса, шкалы, N/A, грубые ошибки, секции и округление в таблицу. Два участника независимо проверяют перенос.
3. Запустить API-каркас и проверить, что все видят одинаковый синтетический ответ.
4. Зафиксировать контракт `Conversation`, `ChecklistVersion`, `CriterionResult`, `Evaluation`, `Appeal`. Владельцем контракта назначается Нариман.
5. Выбрать 12–18 DEV-диалогов для ручной проверки с представлением трёх языков, каналов, N/A и пропущенных действий. Эталон разметить вручную, сохранив спорные случаи.
6. Договориться о формате PR, часах интеграции и ноутбуке, с которого пройдёт защита.

Временные оценки ниже относятся к моменту T0. Если часть времени уже прошла, сначала закрывается ближайшая интеграционная точка.

## Обязательный объём

| Функция | Результат | Кто ведёт |
|---|---|---|
| Импорт | DEV и контрольный набор читаются одним способом, исходные роли и метки времени сохраняются | Нариман |
| Редактор | Изменяются критерий, инструкция, вес, тип, шкала, N/A. Сохранение создаёт версию | Олжас + Нариман |
| AI-проверка | Структурированные ответы на критерии выбранной версии для RU/KZ/EN | Нурхан |
| Доказательства | Существующие реплики, проверенный участок для отсутствующего действия, переход из оценки | Нурхан + Олжас |
| Итог | Расчёт по официальным шкалам и весам, N/A и грубая ошибка, итоги секций при наличии | Нариман |
| Пересмотр | Апелляция на конкретный критерий, решение и причина, история и новый итог | Нариман + Олжас |
| Контроль | Новые диалоги и новый критерий проходят тот же маршрут через интерфейс | Все |
| Сдача | Воспроизводимый запуск, финальный коммит, README и демонстрация за пять минут | Нариман координирует |

После обязательного маршрута можно добавлять фильтры списка, сводку по диалогам и сравнение оценок. Приоритет каждой добавки проверяется по тому, помогает ли она приёмке или защите.

## План по времени

| Время | Нурхан — AI | Нариман — сервер | Олжас — интерфейс | Совместная проверка |
|---|---|---|---|---|
| T0–T+1 | Читает критерии, размечает первые примеры | Поднимает каркас, импортирует DEV, фиксирует контракты | Создаёт Vite/React, подключает синтетические ответы | Все запускают одинаковый пример |
| T+1–T+3 | Первый структурированный ответ модели, сверка цитат | SQLite, импорт, чтение диалогов и чек-листов | Список диалогов, транскрипт, редактор полей | UI показывает диалог из API |
| T+3–T+5 | Проводит один диалог через все критерии | Версии чек-листа, задача оценки и статусы | Запуск оценки, загрузка, ошибки, таблица результата | Один полный реальный маршрут |
| T+5–T+8 | Пропущенные действия, N/A, RU/KZ/EN | Формула из второго PDF, секции, точные тесты | Переход к доказательству, объяснения, N/A и итог | Ручной пересчёт совпадает с сервером |
| T+8–T+11 | Сложные диалоги, звук при необходимости, учёт стоимости | Апелляции, транзакционное решение, история | Подача апелляции и экран проверяющего | Пересмотр меняет итог и переживает перезапуск |
| T+11–T+14 | Проверка нового критерия без правки промпта | Идемпотентность, повторные запросы, восстановление задач | Сохранение новой версии и повторная проверка | Товарищ меняет критерий и проверяет его |
| T+14–T+18 | Прогон DEV, сравнение ошибок, точечные исправления | Полный прогон, журнал состояния и ошибок | Все состояния, клавиатура, длинный текст и адаптивность | Сквозная приёмка по сценарию |
| T+18–T+21 | Фиксирует модель и prompt_version | Сборка frontend, единый запуск, инструкция | Полирует демонстрационный маршрут | Репетиция на другом запуске |
| T+21–T+23 | Проверяет готовность к новому набору | Резервная копия, проверка repo и команды запуска | Стабильные переходы, локальные материалы защиты | Новых крупных функций уже нет |
| T+23–T+24 | Проверяет результаты контрольных диалогов | Импорт контроля, фиксация SHA, готовность сдачи | Проверяет показ результатов | Коммит, отправка ссылки и финальная репетиция |

Длина каждого этапа ориентировочная. Интеграционные точки обязательны, даже если часть улучшений ещё в работе.

## Договорённости между участниками

- Каждый работает в своей ветке. Владение каталогами указано в TEAM.md.
- Первый PR каждого участника должен запускаться на синтетическом контракте.
- Нариман интегрирует в `main` небольшими порциями минимум каждые два часа.
- Изменение общего поля сопровождается примером JSON и обновлением TypeScript/Pydantic.
- Сначала реализуется путь одного диалога. Затем тот же механизм применяется к группе с ограничением параллелизма.
- У каждого сбоя есть понятный статус, сообщение и возможность повторить операцию.
- Исходная оценка и версия чек-листа сохраняются как снимки. Пересмотр добавляет событие решения.

## Что делать при затруднениях

| Ситуация | Действие |
|---|---|
| Второй PDF ещё не получен | Продолжить импорт, навигацию и контракты на помеченном примере. Формула, критические нарушения и исходные восемь критериев ожидают официальных правил |
| Модель даёт неверный JSON | Проверить схему, сделать один ограниченный повтор. При повторном сбое показать `needs_review` и ошибку обработки |
| Цитата отсутствует в транскрипте | Отклонить доказательство и повторно проверить критерий. Статус остаётся видимым пользователю |
| Не хватает звука | Определить применимость по чек-листу. Невозможность проверить критерий отражается отдельно от N/A |
| CORS у источника | Получать набор сервером через официальный GET |
| Задержка модели растёт | Ограничить конкурентность, использовать кэш неизменных входов и измерить p50/p95 |
| Остаётся мало времени | Закрыть новый критерий, N/A, доказательства и апелляцию. Они входят в демонстрацию по ТЗ |

## Готовность

Функция считается готовой, когда работает через интерфейс, сохраняется корректно, проходит свой тест из ACCEPTANCE.md и используется в общем маршруте. Отдельно работающий экран или скрипт проходит интеграцию до закрытия задачи.
