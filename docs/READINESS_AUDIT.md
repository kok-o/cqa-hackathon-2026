# Аудит готовности CQA

**Дополнение от 7 ноября, после этого аудита:** выполнены отдельные
[прогоны со сбоями и пограничными случаями](FAULT_REHEARSAL.md), включая
166 backend-тестов, 15 браузерных fault-сценариев, принудительный перезапуск
тестового сервера и 12/12 новых синтетических чатов через Luna.
Исправлены восстановление очереди, выбор текущего снимка, тайм-ауты и учёт
сбоев. Ниже сохранены результаты прежней репетиции, не смешанные с новым набором.

Срез: **7 ноября 2026 года**, после исправлений импорта, открытия ID со
специальными символами, источников аудио и экспорта. Это независимая проверка
кода и сохранённых свидетельств другим ассистентом; повторных модельных вызовов
в рамках аудита не было.

**Продукт готов к управляемой локальной демонстрации основных сценариев.**
Проверены импорт новых данных, оценка, доказательства, апелляция, версии правил
и ручное воспроизведение звонков. Это не подтверждает экспертную точность,
промышленную нагрузку или прохождение в топ-50. Отдельная проверка живого
HTTP-запуска после изменения чек-листа также завершилась успешно. Реальные
десять контрольных чатов организаторов ещё не получены.

Основание требований: [Guide и приложение](briefs/README.md), официальный
[чек-лист, стр. 1–3](briefs/CQA_Chat_Quality_Checklist.pdf),
[уточнения организаторов](ORGANIZER_CLARIFICATIONS.md) и сценарии
[приёмки](ACCEPTANCE.md). План приёмки сам по себе не считается выполненным тестом.

## Что проверено на живой модели

Источник: локальный игнорируемый отчёт
`data/evaluations/readiness-20261107-live-v1/readiness-report.json` и замороженный
`readiness-plan.json`. Это **10 новых синтетических чатов и 3 синтетических
транскрипта звонков**, созданных до этого запуска. Они не содержат настоящих
контрольных диалогов. Ожидания написаны ассистентом, не передавались модели и
после получения ответов не изменялись.

| Показатель | Результат | Как читать |
|---|---:|---|
| Ответы Luna/high, prompt v6 | 13/13, 0 сбоев провайдера, 0 повторов | Техническое завершение вызова, не полнота всех оценок |
| Чаты: узкие авторские проверки | 33/34; все ожидания совпали у 9/10 примеров | Не официальная accuracy и не все 80 решений восьми критериев |
| Звонки: узкие авторские проверки | 5/7; все ожидания совпали у 2/3 примеров | Не измерение качества распознавания речи |
| Все авторские проверки | 38/41 | Сопоставление с ограниченными ожиданиями, которые сами могут быть спорными |
| Строки чатов в формате PROD | 10 записей: 8 `ok`, 2 `error` | Покрытие полное; успешно оценены 8, а не 10 |
| Дополнительный voice-файл | 3 записи: 1 `ok`, 2 `error` | Проверен общий формат; это не DEV из 65 и не файл для сдачи |
| Задержка одного вызова | средняя 31,38 с; медиана 26,99 с; максимум 77,73 с | Параллелизм 2; не длительность всего пакета и не обещание SLA |
| Расчётная стоимость всех 13 вызовов | 0,02770306 USD | По сохранённой usage, без неизвестных запросов; это оценка по тарифам, не invoice |

Два неполных чата не содержали наблюдаемой работы оператора; у звонков были
обрезанные или недостаточные фрагменты. Обязательные поля не подменялись
предположениями: `needs_review` приводит к строке `error` с причиной.
Неудачное совпадение по C4 относится к бессодержательному совету: модель выбрала
0 вместо авторских 5, и 0 может быть обоснован опубликованной шкалой. Два
расхождения по C3/C8 относятся к неполному ASR: модель сохранила неопределённость
вместо авторских N/A/false. Эти результаты требуют разъяснения границ правил,
а не автоматического исправления под ожидания.

Платная стадия использовала тот же evaluator, что приложение. Следующая стадия
была **in-process FastAPI replay сохранённых исходных ответов** в новой SQLite:
import → jobs → export → validation, без новых обращений к провайдеру. Поэтому
это нельзя описывать как 13 живых модельных запусков из браузера.

## Оставшиеся риски

1. **Нет человеческой или официальной GT.** Структурные тесты, совпадение моделей
   и авторские проверки не дают точность на контроле. Ограниченные смысловые
   обзоры DEV находили спорные границы идентификации, C4/C6 и завершения; часть
   явных ошибок исправлена, отсутствие других не доказано. В защите показывать
   доказательства и пересмотр, не объявлять оценки эталоном.
2. **Нет продуктовой базы знаний.** Содержание тарифов, сроков, защищённых
   операций и достаточных признаков идентификации не получено. По транскрипту
   можно проверить логику и наличие фактов, но нельзя надёжно подтвердить все
   бизнес-рекомендации. Не выдавать догадку о процедуре за установленное правило.
3. **Граница звонков остаётся текстовой.** ASR может искажать роли, формулировки
   и окончание. Telegram допускает N/A для обрезанного приветствия, а JSON 1.0
   требует boolean contact: конфликт источников не разрешён. Сейчас неполнота
   сохраняется явно, без изобретения нового допустимого значения.
4. **Надёжность рассчитана на локальный показ.** Лимит `LLM_CONCURRENCY` — 1–8,
   по умолчанию 2, действует внутри одного процесса. Перезапуск требует повторить
   незавершённую оценку; оплаченный, но ещё не сохранённый ответ может быть
   потерян. Нет проверки промышленной нагрузки, очереди между серверами,
   авторизации пользователей или восстановления после отказа машины. Не
   запускать несколько workers как будто это уже поддержано.
5. **Внешние сервисы и состав группы.** Сеть, провайдер, лимит расходов и срок
   ссылки могут сорвать показ. Upsert сохраняет старые записи, поэтому размер
   группы и предупреждения нужно проверить до экспорта. Сохранённый успешный
   результат полезен для показа истории, но должен быть обозначен как ранее
   рассчитанный, а не новая оценка.

Получить настоящий контроль, импортировать отдельной группой, оценить все
десять, разобрать неполные строки без подмены ответов и проверить
`results/prod/results.json` вместе с DEV. Опубликовать код и результаты в
требуемом собственном публичном GitHub-репозитории, сохранив секреты и исходные
закрытые материалы вне Git; затем передать ссылку по объявленному каналу.

сверки с новыми объявлениями. Развёрнутое приложение не заменяет push; видео
не требуется.

Для живого показа подготовить последовательность: выбранный диалог → цитата
и балл → фильтр грубых ошибок → апелляция → новая версия критерия/веса → новая
оценка → запись звонка. Индивидуальный слот защиты не подтверждён. Организаторы
ожидают работающий продукт и осмысленные оценки; опубликованной формулы,
позволяющей оценить вероятность попадания в топ-50, нет.
