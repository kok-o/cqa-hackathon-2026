# Проверка качества CQA

Эти утилиты измеряют качество на ручной разметке команды. Они не содержат эталонных оценок организаторов и не воспроизводят неизвестную формулу отбора топ-50. При временном чек-листе результаты относятся только к его правилам. После получения официального чек-листа разметку нужно перепроверить.

## Подготовить ручную разметку без вызова модели

Из корня проекта:

```powershell
py -3.13 -m evaluation.cli prepare --dataset data/raw/DEV.json --checklist fixtures/checklist.example.json --out data/evaluations/labels.json --per-language 8 --seed 2026
```

Шаблон содержит до восьми диалогов каждого языка, исходные реплики, снимок чек-листа и незаполненные `expected_results`. Файлы в `data/evaluations/` исключены из Git, поскольку могут включать реальные транскрипты. Существующий файл разметки утилита не перезаписывает.

До разметки проверьте состав выборки: добавьте звонки, отсутствие требуемых действий и случаи N/A. DEV содержит звонки только на RU. У близких шаблонов и переводов установите одинаковый `source_family` и поместите их в одну часть. Автоматическое чередование `dev`/`holdout` — заготовка, а не гарантия отсутствия утечки. Проверка запрещает явно указанный `source_family` в обеих частях.

Для каждого диалога заполните:

- `expected_results`: один ответ на каждый критерий, тип/границы из конфигурации, статус `applicable`/`not_applicable`/`needs_review`, объяснение, точные цитаты или проверенный диапазон. Формат совпадает с контрактом приложения.
- `reviewer`, `review_note`: кто проверил и какие трактовки согласованы.
- `expected_total`: необязательный вручную пересчитанный итог на согласованной шкале; без него MAE итогового балла не вычисляется.
- `reviewed: true`: только после независимой человеческой проверки. До этого диалог не входит в метрики.

Ответы модели не показывайте разметчику до фиксации эталона. Пусть два участника независимо проверят хотя бы шесть диалогов и согласуют расхождения. Используйте `dev` для настройки, `holdout` — после выбора модели и промпта. Если промпт меняется по ошибкам holdout, эта часть уже не является независимой.

## Позже выполнить реальный прогон

После настройки модели в `.env`, команда ниже отправляет **реальные тексты выбранной части** настроенному провайдеру. Без конфигурации она завершается с понятной ошибкой; подставных оценок нет.

```powershell
py -3.13 -m evaluation.cli run --labels data/evaluations/labels.json --split dev --out data/evaluations/pilot-dev.json
py -3.13 -m evaluation.cli score --labels data/evaluations/labels.json --predictions data/evaluations/pilot-dev.json --split dev --out data/evaluations/metrics-dev.json
```

Прогон последовательный, сохраняет результат после каждого диалога, включая сбои. Человеческие ответы не включаются в запрос модели. Итог рассчитывается той же функцией `calculate_score`, что используется приложением. При повторном запуске выберите новый файл, чтобы сохранить историю. Для контрольной проверки замените `dev` на `holdout` в обеих командах.

Вместо результата CLI можно передать JSON-экспорт приложения: массив оценок либо объект с массивом `evaluations`. Для каждого диалога оставьте один запуск по тому же снимку чек-листа; сравнение разных версий или повторяющихся диалогов отклоняется.

При экспорте из приложения метрики используют `original_results` и `original_score`, то есть ответы модели до ручных апелляций. Исправления проверяющего не повышают заявленную точность AI. Пересмотренная оценка без исходных ответов отклоняется. Снимок текста, ролей и временных меток также должен совпадать с размеченным диалогом: одинакового ID недостаточно.

## Как читать отчёт

`decisions.agreement` учитывает совпадение статуса и ответа. Числа 2 и 2.0 равны; boolean и число различаются. `macro_f1` усредняется по наблюдаемым классам «статус + ответ», включая отдельный класс отсутствующего результата; на маленькой выборке смотрите `count` и `observed_classes`. Это внутренняя диагностическая договорённость, а не объявленная метрика организаторов.

MAE числовых ответов рассчитывается только по парам применимых числовых ответов. Вместе с ним показывается число пар; пропуски нельзя скрывать за низким MAE. `missing_or_failed_predictions`, `result_coverage`, `applicable_result_fraction` показывают полноту. `by_criterion` содержит ошибки N/A и ошибки отдельных критериев; `by_language` разделяет RU/KZ/EN.

`quote_existence` проверяет только существование точных цитат, `span_existence` — корректность диапазонов. Они не доказывают смысловую правильность. Для отдельной ручной проверки доказательств можно добавить в копию предсказания поле `evidence_supported_by_human: true/false` в результат критерия; тогда заполняется `semantic_evidence_support`. Без такой проверки значение остаётся неизвестным.

## Настройка адаптера

Требуются `LLM_BASE_URL` (обычно адрес, оканчивающийся `/v1`) и `LLM_MODEL`; облачному провайдеру обычно нужен `LLM_API_KEY`. Поддерживается Chat Completions HTTP API, не нативный Anthropic Messages API. Используются только серверные переменные, ключи не передаются в интерфейс.

- `LLM_JSON_MODE=json_object` — JSON-режим по умолчанию; `json_schema` включает строгую схему; `none` оставляет JSON-инструкцию только в промпте для совместимых сервисов без `response_format`.
- `LLM_TIMEOUT_SECONDS=45`, `LLM_MAX_TOKENS=6000`. Не каждый провайдер/модель поддерживает одинаковые параметры; режим и лимит нужно проверить на пробном диалоге.
- `LLM_INPUT_COST_PER_MILLION`, `LLM_OUTPUT_COST_PER_MILLION` — необязательные актуальные тарифы в USD за миллион токенов. Без обоих тарифов или полного usage стоимость остаётся `null`; нулевую цену система не выдумывает.

На один диалог выполняется один запрос по всем текстовым критериям и максимум один повтор. ID диалога и версии присваивает сервер. Проверяются состав критериев, типы ответов, N/A, точные цитаты, диапазоны и допустимость грубой ошибки. Аудио не загружается; `requires_audio` даёт честный `needs_review`. Учёт токенов суммирует известный usage всех попыток, неизвестный usage отмечается отдельно.

Протокол сверялся с первичными источниками: [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility), [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs). Эти документы описывают совместимость, а не качество оценки RU/KZ/EN. Реальные модельные прогоны в ходе реализации не выполнялись по выбору пользователя.
