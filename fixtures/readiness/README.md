# Новая репетиция готовности: синтетические данные

Набор создан 7 ноября 2026 года после разработки промпта v6, до первого
модельного запуска на этих примерах. Это новые вымышленные тексты, не настоящие
клиентские записи и не контроль организаторов. Узкие ожидания написаны
ассистентом; они могут ошибаться и **не являются человеческой или официальной
ground truth**. До запуска второй ассистент сверил 10 чатов с рубрикой, не
видя ответов модели. Это дополнительный разбор, а не независимая GT-разметка.

| Материал | Состав | Проверяемые ожидания |
|---|---|---:|
| `chats-dataset.json` / `chats-expected.json` | Ровно 10 schema-valid чатов RU/KZ, в том числе смешанные RU/KZ | 34 узких утверждения |
| `voice-dataset.json` / `voice-expected.json` | 3 самостоятельные голосовые транскрипции | 7 узких утверждений |
| `malformed.json` | 5 невалидных API-входов | HTTP 422 без записанных строк |

Английский язык этим новым набором не покрыт. Метки языка соответствуют
контракту RU/KZ; смешанность видна из текста и описания сценария. В голосовых
сценариях стоят заведомо недоступные адреса `example.invalid`: никакое аудио не
предоставлено и не обрабатывается. Выдуманные суммы и учебные счета — части
контролируемых примеров, не факты о продукте.

Чаты проверяют системное подтверждение личности до раскрытия, различение
оператора и бота, исходный язык клиента при другой метке, prompt injection,
личную платную услугу в обход компании, оскорбление оператором, частичную
консультацию, неясное указание, конкретную реакцию на неудобство и объявленное
ожидание без выдуманного SLA-штрафа. Также есть частично сформулированный
запрос, meaningful system-only запись и отдельная пустая реплика внутри
содержательного разговора. Пустой массив транскрипта и полностью пробельный
транскрипт находятся только в malformed-наборе и никогда не посылаются модели.

Ожидания не задают все восемь оценок каждого случая. В частности, на обрезанном
голосовом начале и ASR/неясном завершении не назначены искусственные ответы
C1/C6/C7. Для client/system-only оценка некоторых обязательных критериев может
обоснованно остаться `needs_review`, а строка официального формата — `error`.
**Корректно сохранённая ошибка не равна успешно оценённому диалогу.** Нельзя
подменять её нулём, придуманным положительным ответом или удалять строку.

Ожидания используют canonical JSON SHA-256 датасета и нормализованного
`ChecklistVersion`, как существующий `evaluation.regression`. Runner отдельно
замораживает byte hashes датасетов, ожиданий, malformed, рубрики, промпта и
своего кода в `readiness-plan.json`. Не меняйте их между plan и live. После
получения модельных ответов ожидания нельзя редактировать, чтобы улучшить
процент совпадений; спорные результаты разбираются отдельно с сохранением
исходных ожиданий и ответов.

## Запуск

Из корня репозитория, PowerShell:

```powershell
# Только механическая проверка API, без модели и без оценки semantic quality.
.venv/Scripts/python.exe scripts/readiness_rehearsal.py smoke --suite all --out data/evaluations/readiness-smoke-NEW

# План 10 новых чатов + 3 voice, Luna/high/v6, output16384, timeout180, concurrency2.
.venv/Scripts/python.exe scripts/readiness_rehearsal.py plan --suite all --concurrency 2 --out data/evaluations/readiness-NEW

# Единственная команда с платными вызовами. Максимум авторизованного бюджета $0.25.
.venv/Scripts/python.exe scripts/readiness_rehearsal.py live --out data/evaluations/readiness-NEW --budget-usd 0.25

# Повторить проверки и API replay по сохранённым original outputs — без новых вызовов.
.venv/Scripts/python.exe scripts/readiness_rehearsal.py check --out data/evaluations/readiness-NEW

.venv/Scripts/python.exe -m unittest backend.tests.test_readiness_rehearsal -v
```

`--suite chats` и `--suite voice` создают отдельные планы. Live/check используют
сохранённый suite и параллелизм из плана, не параметры нового запроса.
Каталог должен быть новым и находиться под игнорируемым `data/evaluations/`.
Production-БД и `results/` не используются. Ключ читается существующим
benchmark из окружения/`.env`, не записывается в отчёт и не печатается.

Платная стадия использует существующий budgeted benchmark, который вызывает
тот же evaluator, что приложение, и сохраняет checkpoint, настройки, все
попытки, статистику токенов, время, ошибки и standard-оценки стоимости.
Резерв до запроса покрывает обе разрешённые попытки; бюджет $0.25 общий для
всех продолжений, не добавка. При нехватке бюджета работа пропускается явно.
Unknown usage остаётся неизвестным. Стоимость по токенам не является invoice.
API replay не добавляет расходов и не суммирует сохранённую usage вторично.

Следующая стадия — **in-process FastAPI replay сохранённых результатов**, не
второй платный API-прогон и не проверка живого HTTP-сервера в браузере. В новой
изолированной SQLite она проходит import → evaluation-jobs → submission →
validate, проверяет повторные импорты/ключи идемпотентности и отклонение пяти
malformed-входов. Явно внедрённый evaluator возвращает сохранённые исходные
ответы либо сохранённую ошибку; обращение к провайдеру невозможно в этой стадии.

Для десяти чатов реально вызывается `/api/submission/export?split=prod` и
проверяется покрытие всех 10 исходных ID. Файл называется
`chats-submission-rehearsal.json` и помечен синтетической командой:
**его нельзя сдавать вместо настоящего PROD**. Три voice не превращаются в
DEV из 65: официальный API ожидаемо возвращает 422 для неполного DEV, а
`voice-format-supplement.json` проверяет только общий контракт со `split=None`.

`readiness-report.json` раздельно содержит authored checks, API-результат,
ошибки экспорта и исходную usage/cost. Код выхода 1 означает необходимость
разобрать несовпадения, unresolved/error строки или контрактные проверки;
он не доказывает ошибку модели в каждом таком случае. Код 2 означает ошибку
конфигурации/целостности. Smoke не запускает компаратор ожиданий и не создаёт
показатель качества: его произвольные ответы проверяют только программный путь.

## Браузерная репетиция без модели

Сначала соберите frontend (`npm run build` в `frontend`). В одном терминале
запустите временный сервер; Playwright ему не нужен:

```powershell
.venv/Scripts/python.exe scripts/ui_test_server.py --port 8021
```

Во втором терминале используйте Python, в котором установлен Playwright и
доступен браузер (в текущем окружении это глобальный `python`):

```powershell
python scripts/browser_smoke.py --url http://127.0.0.1:8021
python scripts/browser_readiness.py --url http://127.0.0.1:8021
```

Сервер слушает только `127.0.0.1`, использует `TemporaryDirectory` для SQLite
и явный механический test double, не внешний evaluator. `/api/config` сообщает
`mode=test`; оба браузерных сценария отказываются менять сервер другого режима.
Первый сценарий проверяет основной путь, апелляцию и версии критериев; второй —
10 новых чатов, пограничные входы, отображение аудио и размеры экрана. Аудио во
втором сценарии подменяется синтетическим сигналом в браузере. Эти проверки
не измеряют качество модели или реального распознавания речи. Ctrl+C останавливает
сервер и удаляет временную БД; production-БД и `.env` не изменяются.
