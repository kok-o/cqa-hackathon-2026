# Как пройти весь цикл работы с данными

**Полевая шпаргалка для Data Challenge ’26, 5–6 ноября по Астане.** На хакатоне дадут один реальный кейс Freedom Broker и 24 часа. Начни с контракта задачи и маленького результата, который проходит весь путь от файлов до сдачи. Затем масштабируй то, что уже даёт правильный ответ. Знакомый pandas подходит для компактных задач, Polars LazyFrame удобен для сканирования и преобразований, DuckDB — для SQL, соединений и работы с временным диском. Выбирай по своему запросу, пику памяти и тому, какой код команда успеет проверить. Для практики рядом лежит [оперативный набор](../hackathon-kit/README.md) с профилированием входа, преобразованием в Parquet, шардированием, SQL-примерами и сравнением движков. ## Первые 30 минут дают контракт и валидный пример

| Минуты | Что должно появиться |
|---|---|
| 0–5 | Строка в README с единицей задачи, горизонтом, данными на момент решения, форматом сдачи и метрикой. Пример сабмита и рубрика лежат рядом. У ментора уточнить допуск готового кода, внешних данных и API. |
| 5–15 | Карточка каждого источника с размером, форматом, зерном строки, ключами, полями времени, статусами и валютами. Малый срез для схемы, затем полный профиль тех столбцов, которые участвуют в расчёте. |
| 15–25 | Проверка одного ключевого join. Записать кардинальность, дубли, несовпадения, изменение числа строк и контрольных сумм. Собрать несколько строк результата по образцу. |
| 25–30 | Согласованный split, первое правило или модель и ответственные за данные, расчёт, демо и сдачу. Если таргета нет, определить бизнес-вопрос и знаменатель метрики. |

**Профиль, который ловит реальные сбои.** Сверь число записей, долю пропусков и distinct по ключам, число дублей по составному бизнес-ключу, минимальное и максимальное время. Сравни объёмы по файлу, дню, валюте и статусу. На числах проверь квантили, нули, знаки, хвосты и невозможные значения. Гистограмма и разбивка по датам часто сразу показывают смену масштаба, пропавший день или поток дублей. Срез из первых строк годится для чтения схемы. Для проверки логики добавь редкие статусы и граничные случаи, а для модели отдельно зафиксируй выборку по времени или стабильному ключу. [NIST по разведочному анализу](https://www.itl.nist.gov/div898/handbook/eda/section1/eda11.htm) · [Автоопределение CSV в DuckDB](https://duckdb.org/docs/current/data/csv/auto_detection)

**Сырьё → типизированная таблица → контроль.** Держи оригиналы отдельно. Читай ID строками с первого импорта, чтобы сохранить `0007` и длинные идентификаторы. В pandas проверь `keep_default_na` и свой список `na_values`, если `NA` может быть кодом. Уточни разделитель, encoding, кавычки, десятичный формат и допустимый диапазон. Раздельно считай пустые поля, ошибки приведения и отброшенные парсером записи. Если включил `store_rejects` в DuckDB, проверь журнал и число отвергнутых записей. CSV с переносами внутри кавычек требует счётчика записей парсера. [pandas.read_csv](https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html) · [Ошибки CSV в DuckDB](https://duckdb.org/docs/lts/data/csv/reading_faulty_csv_files) · [Приведение типов](https://duckdb.org/docs/stable/sql/data_types/typecasting)

```sql
WITH typed AS (
    SELECT nullif(trim(amount), '') AS raw_amount,
           try_cast(nullif(trim(amount), '') AS DECIMAL(18, 4)) AS value
    FROM read_csv('ledger.csv', all_varchar = true)
)
SELECT count(*) AS parsed_rows,
       count(*) FILTER (WHERE raw_amount IS NULL) AS missing,
       count(*) FILTER (WHERE raw_amount IS NOT NULL AND value IS NULL) AS invalid
FROM typed;
```

В примере масштаб DECIMAL условный. Для денег согласуй точность и округление, используй DECIMAL либо целые минимальные единицы в проверенном диапазоне. Отдельно учитывай валюту, знак возврата, комиссию и статус операции. При пересчёте валют привязывай курс к согласованному времени и считай долю отсутствующих курсов. Для дат отличай время события от времени доступности записи. Наивные даты сначала локализуй по словарю данных, затем переводи в UTC для вычислений, а календарные дни считай в отчётной зоне. Проверь секунды и миллисекунды в Unix timestamps. [Числа DuckDB](https://duckdb.org/docs/current/sql/data_types/numeric) · [Временные зоны DuckDB](https://duckdb.org/docs/stable/guides/sql_features/timestamps) · [pandas.to_datetime](https://pandas.pydata.org/docs/reference/api/pandas.to_datetime.html)

**Join проверяй до и после.** Уточни полный ключ и где он уникален. Для фактов и справочника в pandas используй `merge(..., validate="m:1", indicator=True)`, предварительно выделив строки с пропущенными ключами. pandas может сопоставить null с null, обычное SQL-сравнение `=` такие ключи пропускает. В DuckDB `ANTI JOIN` покажет потерянные ключи, `SEMI JOIN` — наличие совпадения без копирования правых строк. Сверь число строк, distinct ID фактов, сумму и сумму модулей по валюте. Один дубликат справочника способен раздуть объём данных и денежный итог. Для последней котировки или статуса подходит ASOF назад, с проверкой возраста значения и времени его доступности. Равные таймстампы разрешай по осмысленному tie-break. [pandas.merge](https://pandas.pydata.org/docs/reference/api/pandas.merge.html) · [DuckDB JOIN и ASOF](https://duckdb.org/docs/stable/sql/query_syntax/from)

## Движок выбирают по операции и пику памяти

| Что предстоит | С чего начать | Что проверить |
|---|---|---|
| Файлы, промежуточные таблицы и выход помещаются с запасом | pandas с `usecols`, явными типами и векторными операциями | Размер результата join, копии и конвертации перед обучением |
| Большой CSV, нужны несколько агрегатов | `pd.read_csv(..., engine="c", chunksize=...)` | Объём состояния между чанками. `low_memory=True` всё равно возвращает целый DataFrame |
| Много столбцов или файлов, фильтры и преобразования | `pl.scan_csv` или `pl.scan_parquet`, lazy-выражения | `explain()` и физический план streaming, особенно после Python UDF, окон и тяжёлых join |
| Большие join, дедуп, окна, SQL на нескольких файлах | DuckDB с локальным scratch на SSD | `EXPLAIN ANALYZE`, кардинальности, RAM и свободное место под spill |
| Много повторных чтений одной схемы | Один раз записать нужные столбцы в Parquet | Сколько времени займёт конвертация и какие фильтры смогут отсечь чтение |

[pandas по большим данным](https://pandas.pydata.org/docs/user_guide/scale.html) · [Polars Lazy](https://docs.pola.rs/user-guide/lazy/optimizations/) · [DuckDB workload tuning](https://duckdb.org/docs/guides/performance/how-to-tune-workloads)

В Polars `scan_*` позволяет протолкнуть выбор колонок и фильтры к чтению. `read_csv(...).lazy()` уже прочитал CSV целиком. Parquet дополнительно позволяет пропустить группы строк по статистике, когда фильтр подходит. **Большой выход пиши прямо на диск.** Для компактного результата подходит `collect(engine="streaming")`. Потоковый режим способен сократить память, а тяжёлые операторы могут потребовать буферизацию или перейти к выполнению в памяти. У DuckDB `memory_limit` относится к буферному менеджеру, полный RSS процесса может быть выше. При росте памяти проверь объём результата, сократи входы, число потоков или раздели запрос на стадии. `COPY (SELECT …) TO 'out.parquet' (FORMAT PARQUET)` сохраняет выдачу без полной материализации в pandas. [Polars Streaming](https://docs.pola.rs/user-guide/concepts/streaming/) · [Polars sink_parquet](https://docs.pola.rs/api/python/stable/reference/lazyframe/#polars.LazyFrame.sink_parquet) · [DuckDB OOM](https://duckdb.org/docs/current/guides/performance/oom) · [DuckDB Parquet](https://duckdb.org/docs/stable/data/parquet/overview)

```python
import polars as pl

q = (
    pl.scan_parquet("stage/events.parquet")
    .filter(pl.col("status") == "success")
    .select("client_id", "event_ts", "amount_minor")
)
print(q.explain())
q.sink_parquet("stage/success.parquet", engine="streaming")
```

**Замеряй свой маршрут.** Возьми один представительный запрос и одинаковые колонки, типы, фильтры и выход для всех движков. Сначала сверяй строки и контрольные агрегаты. Потом меряй время до готового результата и пик RSS в свежих процессах, отдельно первый и повторный проход. Размер файла и `DataFrame.memory_usage(deep=True)` помогают оценить вход, а пик процесса захватывает промежуточные выделения. На Windows `tracemalloc` покрывает Python-аллокации, для общей памяти используй системный замер. Папку временного spill удобно вынести на локальный SSD за пределы OneDrive. [psutil](https://psutil.readthedocs.io/) · [tracemalloc](https://docs.python.org/3/library/tracemalloc.html) · [DuckDB EXPLAIN ANALYZE](https://duckdb.org/docs/current/guides/meta/explain_analyze)

### Чанки и шарды решают разные задачи

**Чанк** — следующая порция записей. **Шард по ключу** собирает все нужные совпадения вместе. От способа склейки зависит правильность итоговой метрики.

| Операция | Что хранить или как разделить |
|---|---|
| Count, sum, min/max | Объединять частичные итоги. Явно определить результат для группы из одних null. |
| Среднее, доля, взвешенное среднее | Сумма и число валидных, числитель и знаменатель либо `Σ(x·w)` и `Σw` по одной маске. Среднее частичных средних с разными весами сместит итог. |
| Exact distinct и дедуп | Общий set, пока он помещается, либо шарды по ключу. Для distinct по группам можно шардировать по паре «группа, ID» и складывать количества уникальных пар. |
| Join большого файла и малого справочника | Проверенный уникальный справочник в RAM, факты порциями. |
| Join двух больших таблиц | DuckDB со spill либо одинаковые бакеты по ключу на обеих сторонах. Крупнейший бакет должен укладываться вместе со своим выходом. |
| Квантили и приближения | Точный квантиль по общим данным. При допустимой погрешности — sketch через `approx_quantile` или `approx_count_distinct` и явная маркировка. Усреднение квантилей чанков даст другую величину. |

[pandas chunking](https://pandas.pydata.org/docs/user_guide/scale.html#use-chunking) · [Агрегаты DuckDB](https://duckdb.org/docs/stable/sql/functions/aggregates)

Пример поточного среднего по числовой колонке. Размер порции подбери по замеру.

```python
import pandas as pd

total, n = 0.0, 0
with pd.read_csv(
    "ledger.csv",
    usecols=["value"],
    dtype={"value": "Float64"},
    engine="c",
    chunksize=100_000,
) as chunks:
    for chunk in chunks:
        values = chunk["value"].dropna()
        total += float(values.sum())
        n += len(values)

mean = total / n if n else None
```

Этот расчёт проходит по всем значениям с обычным float-округлением. Для денежных контрольных сумм используй согласованное точное представление. При сверке distinct учти разницу по умолчанию. В Polars `n_unique()` включает null, в pandas `nunique()` пропускает. [pandas.read_csv](https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html) · [Polars n_unique](https://docs.pola.rs/api/python/stable/reference/expressions/api/polars.Expr.n_unique.html)

Для хеш-шардирования зафиксируй нормализацию ключа, политику null, функцию, seed, версию и число бакетов. Схема `stable_hash(key) % B` размещает ключ, а join и дедуп внутри бакета сравнивают исходное нормализованное значение. Python `hash(str)` меняется между процессами, стабильность `Polars.hash` ограничена версией. Составной ключ сериализуй однозначно. Проверь размеры бакетов и горячие ключи. Если один ID даёт огромный объём, рост числа бакетов его целиком сохранит в одном месте. Для outer join включай бакеты, присутствующие только на одной стороне. [Хеширование в Python](https://docs.python.org/3/reference/datamodel.html#object.__hash__) · [Polars Expr.hash](https://docs.pola.rs/api/python/stable/reference/expressions/api/polars.Expr.hash.html)

**Партиция по месяцу** полезна для типичных запросов по периоду. Для join по клиенту пригоден layout по хешу клиента. Если историю разбить по датам, rolling и последняя операция потребуют контекста из соседних партиций. Начни с простого Parquet, добавляй партиции под повторяемый фильтр или тяжёлый join. Избегай множества мелких файлов. Каждый прогон пишет в отдельную папку с manifest, где указаны схема, входы, ключ, строки, параметры и версия. Сверь результат с простым расчётом на фикстуре с повторяющимся ключом через границу чанка, пропуском и дубликатом. [Arrow Dataset](https://arrow.apache.org/docs/python/dataset.html) · [DuckDB Hive Partitioning](https://duckdb.org/docs/current/data/partitioning/hive_partitioning)

## От строк к метрике, модели или маршруту

### Клиентские события и операции

**Воронка.** Определи, считаешь клиентов или заявки. Найди первый signup и следующую успешную стадию той же заявки в правильном порядке. Учебная цепочка Freedom — регистрация → KYC → пополнение → первая сделка. Зафиксируй окно и считай только зрелые когорты, у которых это окно полностью наблюдается. Покажи две конверсии, от исходной базы и от предыдущего шага. В подписи к графику укажи размер когорты, период и правило совпадающих таймстампов. Для удержания можно строить тепловую карту по неделе входа и неделе жизни когорты, показывая только наблюдаемые ячейки. [Кейс онбординга Datathon’25](https://kz.linkedin.com/in/adilkhanalpysbay) · [DuckDB ASOF и JOIN](https://duckdb.org/docs/stable/sql/query_syntax/from)

**RFM.** Выбери дату среза. R — сколько прошло с последнего релевантного действия, F — число уникальных заказов за окно, M — выбранная денежная величина в сопоставимой валюте. Частичные исполнения и возвраты разбери отдельно. Для каждого сегмента покажи его размер, профиль и следующее действие. Если есть история эксперимента, анализируй по единице рандомизации, сравни фактические размеры групп с назначенным соотношением и покажи разницу с интервалом неопределённости. Если перед тобой историческая воронка, её провал — гипотеза для теста. Предложи изменение, основную метрику и показатель, который должен остаться в допустимых пределах. [RFM-кейс Freedom Broker в SDU](https://astanahub.com/ru/blog/put-k-pobede-kak-vypusknik-data-science-academy-stal-priziorom-freedom-data-challenge-20251750765587) · [Microsoft Research о проверках A/B](https://www.microsoft.com/en-us/research/publication/diagnosing-sample-ratio-mismatch-in-online-controlled-experiments-a-taxonomy-and-rules-of-thumb-for-practitioners/)

### Прогноз, ранжирование или поиск аномалий

**Делай признаки такими, какими они были в момент решения.** Для клиента в момент `t` возьми прошлые события из `[t−W,t)` и проверь `available_at <= t`. Таргет из `(t,t+H]` формируй только при полном горизонте. У обучающих строк результат должен успеть стать известным к началу валидации. Для будущих событий дели по датам, для новых клиентов — по группам, для обоих требований отдельно проверь поздних новых клиентов. Импутацию, кодировщики и отбор признаков обучай внутри train. Одинаковый split и seed для всех сравнений. В `TimeSeriesSplit` параметр `gap` измеряется строками. Для реального разрыва по времени на неравномерных событиях задай даты явно. [Point-in-time joins](https://docs.feast.dev/getting-started/concepts/point-in-time-joins) · [Ошибки валидации scikit-learn](https://scikit-learn.org/stable/common_pitfalls.html) · [TimeSeriesSplit](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)

| Постановка | Быстрый baseline | Проверка вдобавок к официальной метрике |
|---|---|---|
| Редкое целевое действие | Текущее правило → логрег или CatBoost | AP, precision и recall@K при реальном размере очереди |
| Числовой прогноз | Медиана → дерево или бустинг | MAE в исходных единицах, ошибки по группам и на хвостах |
| Тикер-день или спрос | Последнее значение или сезонный наивный прогноз | Backtest по датам, лаги доступны на момент прогноза, издержки учтены при оценке стратегии |
| Ранжирование | Популярность за прошедший период | Recall@K и NDCG@K по запросу или клиенту на будущих событиях |
| Подозрительные события без меток | Порог либо медиана и MAD внутри сопоставимой группы | Ручная проверка верхних K, объяснение, размер очереди |

[AP](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html) · [NDCG](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html) · [CatBoost fit](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier_fit)

Если train большой, сначала сократи признаки и посчитай baseline на зафиксированном срезе, затем увеличивай объём. Для батчевого обучения простого классификатора есть `SGDClassifier.partial_fit`. Веса классов или сэмплинг применяй в train, а порог для реальной очереди выбирай на репрезентативной валидации. На защите переводи метрику в сравнение при равном ресурсе. Если в очереди из 100 мест модель нашла 22 известных позитива, а правило 14, это восемь дополнительных попаданий в исторической проверке. Эффект самого действия измеряется отдельным экспериментом. [Батчевый SGD](https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.SGDClassifier.html) · [Выбор порога](https://scikit-learn.org/stable/modules/classification_threshold.html)

### Текст, обращения и документы

**Извлечение полей и обязательные правила проверяй отдельно.** При наличии разметки начни с символьных n-грамм TF-IDF и логрега. Дубли обращения держи в одном фолде, проверь редкие классы, смешанный RU/KZ/EN, транслит и пустой текст. Если ТЗ допускает LLM, валидируй выход по схеме, выделяй таймауты и ручную очередь. Роутер применяет правила назначения, возвращает причину и проверяет повторный ID. Измеряй macro-F1 классификации, нарушения правил, долю ручной обработки и p95 времени. Для кейса с документами сделай набор вопросов с эталонными источниками, измерь попадание нужного источника в top-K и корректность цитат. Условия передачи текстов, адресов и вложений во внешние сервисы уточни по правилам кейса. ## Один воспроизводимый запуск и три доказательства для защиты

**До старта** проверь окружение на ноутбуке, с которого будете сдавать. Закрепи версии пакетов, собери локальные wheels под ту же ОС и Python через `pip download` и проверь установку с `--no-index --find-links=wheelhouse`. Прогони без сети маленький маршрут от CSV до модели или демо. Если нужны локальные веса или токенизатор, проверь их наличие тем же способом. Команде хватит одного ответственного за сборку и общей схемы витрины. Фиксируй в README входы, версии, срез, команду запуска, пути выходов и владельцев. [pip download](https://pip.pypa.io/en/stable/cli/pip_download/) · [pip install](https://pip.pypa.io/en/stable/cli/pip_install/)

**По ходу суток** сделай первый сквозной результат в начале, затем проверенный расчёт на полном объёме. Улучшения вводи по одному с записью метрики и стоимости прогона. Финальные часы оставь на заморозку артефактов, запуск с чистыми путями и отправку. Перед сдачей сравни с образцом число строк, ключи, порядок столбцов, типы, допустимые диапазоны, пропуски и бесконечности. Сохрани предыдущий валидный результат. На случай проблем с сетью держи локальную копию графиков и демонстрации.

**Для защиты** подготовь три кадра. Первый показывает, где возникает проблема и сколько людей или операций она затрагивает. Второй сравнивает baseline и итог на одном срезе, с размером выборки и единицами. Третий проводит один пример от входа до решения или действия. Для воронки подойдут столбцы с `n` и процентами, для когорт — тепловая карта, для роутера — карточка обращения с причиной назначения. Указывай период, валюту, знаменатель и границы применимости. Для бизнес-эффекта отдельно подпиши измеренный результат и предположения. Передай вместе с демо команду воспроизведения, чтобы жюри могло проверить любой показанный показатель.
